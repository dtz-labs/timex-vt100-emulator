# Performance review: font rendering and scrolling

**Date:** 2026-07-26  
**Scope:** read-only review of the current 64-column renderer, scrolling paths,
and the pending 80-column implementation plan.

## Verdict

Large precomputed font tables are not the best first optimisation. The font is
already stored in a representation that can be written directly to video RAM.
Most time is lost through whole-row repaint amplification, code generated by
SDCC for `dst[8]`, and repeated address calculations during scrolling.

The 80-column renderer from the current implementation plan should not be
implemented as written. Its measured cost is substantially worse than assumed
by the design.

## Measurements

Measurements used the repository's target flags:

```text
zcc +zx -SO3 -clib=sdcc_iy
```

The figures come from `z88dk-ticks`. They measure CPU T-states and do not include
Timex display-memory contention, so target latency can only be worse.

| Path | Current or planned code | Diagnostic variant | Improvement |
|---|---:|---:|---:|
| One normal dirty row, 64 columns | 176,039 T | 76,055 T | 2.31x |
| Screen-model scroll | 449,787 T | 67,609 T | 6.65x |
| Video-RAM scroll | 682,052 T | 345,464 T | 1.97x |
| Planned 80-column row | 670,861 T | 194,617 T | 3.45x |

Additional baselines:

- Full current repaint: 4,159,179 T, approximately 1.19 s at 3.5 MHz.
- Current model plus VRAM scroll primitives: 1,131,839 T, approximately 323 ms.
- A real LF may also repaint a row before and after scrolling, bringing the
  lower-bound cost to approximately 424 ms before parser and contention costs.
- The planned 80-column C renderer extrapolates to approximately 4.6 s for a
  full repaint.

## Findings

### P0: one character repaints the whole row

`screen_putc()` marks one boolean `dirty[row]` (`src/screen.c:33-51`), but
`render_flush()` repaints all 64 cells in that row (`src/render.c:85-121`).
`main.c:89-110` additionally dirties the old and new cursor rows.

Consequently, a one-character update performs 64 glyph lookups and 512 video
stores. This is especially damaging with the Interface 1 backend: `conn_poll()`
collects at most two RX bytes per call (`src/conn.c:34-40,313-337`), and the main
loop immediately renders received data (`src/main.c:281-299`).

For the future 80x6 layout, track dirtiness in groups of four cells. Four cells
are exactly the packer's natural unit of three bytes. Twenty groups per row need
three dirty bytes, or 72 bytes for all 24 rows.

The cursor should be toggled with XOR before processing an input batch and again
after rendering, rather than marking whole rows dirty.

### P0: the scroll and dirty-state contract is fragile

`main.c:92-94` pre-flushes video RAM only for a raw LF byte or deferred wrap.
The parser can also scroll for VT and FF (`src/vtparse.c:143-150`) and for
`ESC D`, `ESC M`, and `ESC E` (`src/vtparse.c:431-447`). In those cases the
hardware scroll can move stale pixels or an inverted cursor.

After copying video memory, `render_scroll_region()` clears all dirty flags in
the region (`src/render.c:183-185`). That can discard pending changes which were
not present in video RAM.

There is another hidden dependency during deferred wrap: `screen_putc()` first
scrolls and then writes the new character (`src/screen.c:35-41`). The hardware
scroll is handled only after `vt_feed()` returns, and clears the new dirty flag.
`main.c:110` accidentally saves the character by dirtying the whole bottom row
again. That line cannot simply be removed.

The robust model is:

1. Toggle the old cursor off.
2. Move dirty-group metadata together with the corresponding cell rows.
3. Copy video RAM for the scroll.
4. Leave moved dirty groups pending, instead of clearing the whole region.
5. Render only those groups and toggle the new cursor on.

This removes the raw-byte scroll prediction from `main.c` and preserves
correctness for every parser path.

### P0: the current font layout is already suitable; the blitter is not

`src/font_data.h` stores glyphs as `[glyph][8]` in Timex scanline byte order.
For the normal attribute path, `src/render.c:42-49` writes the eight bytes
without shifts, masks, or conversions.

The expensive part is `render_cell_to()` accepting `dst[8]`. With the current
SDCC flags, the generated function has a 28-byte stack frame and approximately
632 bytes of code. It reloads destination pointers and adds `bx` repeatedly,
and is called 64 times per row.

A diagnostic C fast path which:

- computes the address of scanline zero once,
- writes subsequent bytes at offsets `0x000` through `0x700`, and
- handles `attr == 0` separately,

reduced a row from 176,039 T to 76,055 T. A scanline-first implementation which
cached 64 glyph pointers was slower at 121,893 T.

Keep the existing glyph-major font for the current renderer. Add a tight normal
path, with reverse and underline handled by a slower fallback. A completely
blank row can also be detected and cleared blockwise without any additional
font data.

### P0: scrolling can be made about 2.7 times faster in C

The screen model currently copies every two-byte cell through nested loops and
16-bit index arithmetic (`src/screen.c:79-127`). A single overlapping `memmove()`
for the retained rows, followed by blanking the released rows, reduced the cost
from 449,787 T to 67,609 T.

The video path already compiles `memcpy(..., 32)` into `LDIR`, so merely replacing
it with handwritten `LDIR` will not help. The problem is that
`src/render.c:132-164` repeatedly calculates both source and destination
addresses for every scanline and then repeats the work for the second display
file.

Computing a text-row base once, handling both files in one loop, and moving to
the next scanline by increasing the address high byte reduced the video scroll
from 682,052 T to 345,464 T. No large lookup table is required; an optional
24-entry row-base table would cost only 48 bytes.

The fast path should also support arbitrary `n`. At present
`render_scroll_region()` accepts only `n == 1` and `n == -1`
(`src/render.c:166-181`). `screen_insert_lines()` and `screen_delete_lines()` do
not update `scroll_seq` (`src/screen.c:211-225`), so IL and DL still trigger a
full region repaint.

### P0: the planned 80-column renderer is not performance-ready

Task 5 in `docs/superpowers/plans/2026-07-26-80-column-rom-font.md:923-975`
collects 80 glyph pointers and attributes and then performs, per row:

- 80 calls to `font_glyph()`;
- 640 calls to `glyph_row_byte()`;
- 160 calls to `render_pack4()`;
- repeated round-trips through local `g[8]` and `packed[3]` arrays.

A faithful target build of this code measured 670,861 T per normal row, around
192 ms. This is 3.8 times slower than the current 64-column row and worse than
the design's estimated 2-3 times slowdown
(`docs/superpowers/specs/2026-07-26-80-column-rom-font-design.md:224-235`).

Inlining the normal packer reduced the result to 194,617 T. The target renderer
therefore needs:

- an inline group loop for `attr == 0`;
- group-level attribute detection so only affected groups use the slow path;
- no helper calls or temporary arrays inside the normal hot loop;
- an assembly normal path if the C implementation still misses the target.

The existing D16 decision and the plan's instruction to optimise only after the
80-column implementation are superseded by the new performance requirement.

### P1: large font lookup tables are constrained by the IM2 layout

The current default build ends at `0xCD58`. `main.c:190-206` writes the IM2 table
at `0xD300` and its trampoline at `0xD4D4`, leaving only 1,448 bytes before the
first unmodelled runtime reservation. The linker does not know about these
absolute writes.

The planned `row_glyphs[80]` and `row_attrs[80]` add 240 bytes before any renderer
code growth. A link can therefore succeed while producing an image which will be
overwritten during IM2 setup.

An assembly renderer could benefit from eight page-aligned 256-byte font pages,
`FONT_SCANLINE[8][256]`: the scanline selects the address high byte and the
character code becomes its low byte. This would use 2 KB instead of the current
1 KB, plus up to 255 bytes of alignment. It should be considered only after the
IM2 area is explicitly reserved or relocated and after a map-file limit check is
added.

Four pre-shifted phases or full attribute variants would require roughly 4-8 KB.
They are not justified: constant rotations and `CPL` are cheap in assembly, and
masks and OR operations remain necessary even with such tables.

### P1: performance needs a reproducible gate

The native tests cover only the pure renderer helpers; hardware writes are not
executed by `test/test_render.c`. The smoke test validates selected startup
pixels but not scroll correctness or latency.

A target performance harness should measure:

- one dirty cell or four-cell group;
- one row with normal, reverse, underline, and mixed attributes;
- a blank row and full repaint;
- model and VRAM scroll up and down;
- full and partial regions crossing rows 7/8 and 15/16;
- arbitrary `n`, IL, DL, LF, VT, FF, deferred wrap, IND, RI, and NEL;
- cursor hide/show and dirty state after each scroll;
- final program/data address relative to `0xD300` and stack high-water usage.

The CI image currently uses `z88dk/z88dk:latest`
(`.github/workflows/ci.yml:39-48`). Any T-state regression threshold requires a
pinned compiler image or digest and recorded compiler version.

## Recommended implementation order

1. Add repeatable `z88dk-ticks` benchmarks and a map/IM2 overlap check.
2. Replace row booleans with dirty four-cell groups and implement exact cursor
   hide/show.
3. Preserve dirty metadata correctly across every scroll event.
4. Replace cell-by-cell model scrolling with block `memmove()`.
5. Hoist video text-row addressing, handle both files together, and support
   arbitrary `n` including IL and DL.
6. Implement the 80-column normal group packer inline, with a blank-row fast path
   and an attribute fallback.
7. Add a Z80 assembly normal path if the benchmark still warrants it.
8. Only then benchmark a page-aligned scanline-major font or a small lookup table.

If the current 64-column release must be accelerated before the 80-column work,
the direct glyph-major `attr == 0` path is a low-data-cost intermediate change.
If the project is moving directly to 80 columns, the reusable dirty-tracking and
scroll changes should be implemented first instead of landing a throwaway
64-column font transpose.
