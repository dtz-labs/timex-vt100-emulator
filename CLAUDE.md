# Repository Guidelines

## Project Structure & Module Organization

This repository is a C implementation of a VT-102 terminal core, built from one source tree into two TAPs: an 80x24 Timex TC2048/TC2068/TS2068 build using SCLD hi-res video, and a 40x24 ZX Spectrum 48K/128K build using plain ULA video (the ZX build also runs on a Timex, since a Timex boots in Spectrum-compatible ULA mode; the Timex build refuses to run on a machine without an SCLD rather than paint an unreadable half-image). Runtime code lives in `src/`, with matching public headers in `include/`. Keep pure, host-testable logic in modules such as `screen.c`, `vtparse.c`, `keybuf.c`, and `conn.c`. Hardware isolation is split by concern and by machine: `machine.c` (SCLD detection), `video_hires.c`/`video_ula.c` (video mode init), `render.c` plus its geometry alternatives `render_hires.c`/`render_ula.c` (cell-to-pixel mapping), and the target-only, non-host-testable blitters `blit_hires.c`/`blit_ula.c` (absolute video-RAM writes). `render_hires.c`/`render_ula.c` and `blit_hires.c`/`blit_ula.c` are alternatives exporting the same symbols -- never link both into one binary. Which side of each pair is built is selected by exactly one of `TERM_TIMEX` or `TERM_ZX` (a compiler define, not a user-overridable knob -- see `TARGET_DEFS` in the Makefile); `screen.h` `#error`s if neither or both are defined, since that same define also sets `COLS` (80 or 40). Host tests live in `test/test_*.c`, with `test/run.sh` as the canonical fast test runner; the geometry-sensitive suites (`test_screen`, `test_vtparse`, `test_render`) compile and run twice, once per `TERM_DEF`, while the rest compile once with no machine define at all (they don't include `screen.h`). The audio-link backend follows the same split: `alink_frame.c` and `alink_slave.c` are pure protocol logic and host-tested, while `alink_phy.c` is target-only (absolute ports, cycle-counted loops) and must never reach a host-test link line, exactly like `blit_*.c`; `tools/alink/` is the PC side and `docs/audio-link-setup.md` the how-to. `tools/genfont.py` maintains font data, and `docs/superpowers/specs/` contains design decisions and target-toolchain notes. Treat `build/`, `*.tap`, `*.bin`, and `*.map` as generated artifacts unless explicitly updating release outputs.

## Build, Test, and Development Commands

- `test/run.sh`: compiles and runs all native host unit tests with `cc`, `-std=c99`, `-Wall`, `-Wextra`, and `-Werror`, in both the `TERM_TIMEX` and `TERM_ZX` passes.
- `CC=clang test/run.sh`: runs the same tests with a selected compiler.
- `export PATH="$HOME/Programowanie/z88dk/bin:$PATH"` and `export ZCCCFG="$HOME/Programowanie/z88dk/lib/config"`: prepare the z88dk target toolchain.
- `make ci`: the full host gate (`test/run.sh` plus every Python suite and the terminfo check). Needs no z88dk. Run it before committing.
- `make tap`: builds the Timex 80-column `.tap` (`build/term.tap`). `make tap-zx`: builds the ZX Spectrum 40-column `.tap` (`build/term-zx.tap`). `make if1`/`make if1-zx` add the Interface 1 RS-232 backend to each, `make audio`/`make audio-zx` the tape-port audio backend (`build/term-audio.tap`, `build/term-zx-audio.tap`). Six shipped images in total, all gated by `make check-image-limit`. (Do not hand-roll a `zcc ... src/*.c` command: `render_hires.c`/`render_ula.c` and `blit_hires.c`/`blit_ula.c` are alternatives that export the same symbols and must never both be linked in -- see the Makefile's `TIMEX_SOURCES`/`ZX_SOURCES` for the exact, non-wildcard source lists.)
- Adding a build variant means adding its TAP to the `$(ZX_TAP) $(ZX_IF1_TAP) $(ZX_AUDIO_TAP): TARGET_DEFS := -DTERM_ZX` line **below every `*_TAP` variable it names**: Make expands a target-specific variable line's target list when it reads the line, so a name defined later expands to nothing and that build silently inherits the global `-DTERM_TIMEX`. This produced a `term-zx-audio.tap` that compiled, linked, passed the image-limit gate and then halted on a 48K with the SCLD guard.
- `/Applications/ZEsarUX.app/Contents/MacOS/zesarux --machine TC2048 --tape build/term.tap`: runs the Timex build in ZEsarUX. Use `--machine 48k --tape build/term-zx.tap` for the ZX build.

## Coding Style & Naming Conventions

Use C99, four-space indentation, K&R-style braces as in existing sources, and concise block comments only where they clarify non-obvious behavior. Prefer fixed-width aliases from `include/types.h` (`u8`, `s8`, `u16`, `s16`). Keep APIs pointer-oriented: pass structs by pointer or out-pointer, and avoid returning structs by value for SDCC/z88dk compatibility. Do not introduce float, malloc, recursion, or headers that shadow z88dk system headers.

## Testing Guidelines

Add or update `test/test_<module>.c` for pure logic changes. Tests use plain `assert` plus local `CHECK` counters, so keep cases explicit and deterministic. Run `test/run.sh` (or `make ci`) before committing. Hardware-facing behavior must be verified with ZEsarUX: `make smoke`/`make smoke-zx` (`test/zesarux_smoke.py`) drive the ZRCP builds, and `make smoke-audio` (`test/alink_zesarux.py`) drives the audio link in both directions. Prefer a new scenario in one of those two harnesses over a new script. Two rules this project keeps relearning: a test that cannot fail is not a gate, so mutation-test anything claimed to be one -- break the thing it guards and watch it go red; and when a test fails, first ask whether the *test* is wrong, because here it has been, repeatedly.

## Commit & Pull Request Guidelines

Recent commits use scoped, imperative subjects such as `vtparse: add CSI erase handling` or `screen: scroll region set`. Prefer `module: concise change`, and mention `host TDD` when tests drive the change. Pull requests should describe behavior changes, list test/emulator commands run, link relevant specs or issues, and include screenshots or RAM/smoke-test artifacts for visible TC2048 rendering changes.
